# JSONL 协议与优化后的解题方案（2026-11-10）

## 先满足协议，再测量内核优化

本版合并官方提交 `f4d4e26653af823a7601668802f80e374ad6643c` 的 STDIO_PROTOCOL.md、protocol_check 和题库说明。
这些官方文件保持原样。生产镜像默认启动 JSONL；测试用旧文本接口须显式使用 --protocol legacy，或 minivectordb_legacy。

数据库构造和恢复完成后才输出唯一的 ready 对象。每条请求原样回传 id，SQL 从已解码 JSON 字符串中取出，
不会按通信输入中的分号切割。Result 增加逐列类型元数据，BIGINT 通过 from_chars 转成 int64 JSON 整数，
VARCHAR 保留字符串，浮点和向量返回有限 JSON 数值／数组；不凭字符串内容猜类型，空查询仍保留列名。
错误为 ok:false 和非空 error.code，SQL 错误后继续处理下一请求。每次请求调用 set_search_mode，
它只改变检索模式，不重启数据库，不丢弃事务状态。shutdown 先销毁数据库、回滚未提交状态，再响应并退出。

JSON 使用允许的通用序列化库 nlohmann/json 3.11.3，固定头文件 SHA-256、保留 MIT 许可；
存储、索引、执行与事务仍为自研。基础镜像 digest 和直接 apt 包版本锁定于 DEPENDENCIES.lock.json。
APT 镜像仓库及传递依赖的长期可用性仍是外部条件。

## 保持精确性与持久性边界

- 精确 TopK 沿用标量 double 的最终距离与 PK 并列规则；已有 SIMD/FMA/AVX-512 只做保守候选淘汰。
- 本次将浮点解析改为 from_chars 快路径；下溢、空白等边界退回原 strtod，保留有限 float32 与维度检查。
- publish 中用最多 1MiB 的缓冲合并连续 Heap 和 COW 索引页写入，批量减少 pwrite 调用。
- WAL 先 fdatasync，再发布 Heap/索引，再同步 manifest 与目录的顺序完全保留；没有延迟提交确认或省略 fsync。
- MVDB_BATCH_WRITES=0 可禁用写合并用于诊断；正式镜像默认启用。额外缓冲有固定上限，不随数据库总量增长。
- exact 是性能测试的固定模式；保留 IVF 与事务维护，未使用低召回的少量探测桶换取分数。

## 实际验证

1. 官方发布工具驱动真实生产镜像：握手通过，20/20 组、95/95 SQL 通过，含正常重启和每请求 ann 切换。
2. CTest 16/16：原有 SQL/存储/故障/ANN/SIMD 回归使用同一核心的 legacy 可执行文件；新增 JSONL 测试使用生产入口，
   检查超过 JS 安全整数的 BIGINT、id 类型、空列集、向量数组、Unicode、换行/制表符/分号/引号、事务内模式切换、
   预期错误、无效报文后继续交互、shutdown 回滚和强杀重启。
3. 生产 JSONL 在 64MiB cgroup 硬限制且无 swap 下写入 200,000 x 128 维记录，Heap 为 109,400,000 B，
   超过 67,108,864 B 内存限制。无 OOM/oom_kill，过滤和无过滤 TopK、尾部范围、重启点查均通过。
   这是缩小内存预算的外存压力证据，不等于全部隐藏资源测试。
4. 锁定依赖后重新构建，最终生产二进制 SHA-256 与测量及回归版本完全相同；再次通过官方握手和全公开用例。

## 三轮交替 A/B

基线也已接入 JSONL，仅缺本次写合并与浮点解析优化；没有用旧文本协议结果直接充当基线。
顺序为 baseline-1, optimized-1, optimized-2, baseline-2, baseline-3, optimized-3。每轮独立 Linux 数据卷、2 CPU / 2GiB / 128 PID、无 swap、无网络，
10K x 128 向量，1000 次 Top10（半数带过滤），30 次预热。每轮全量核对1000次查询，
另起未计时容器重启并逐条核对全部10K行、普通列和float32向量。

| 三轮中位数 | JSONL 基线 | 优化后 |
| --- | ---: | ---: |
| 写入秒 | 2.859 | 2.469 |
| 查询秒 | 0.922 | 0.828 |
| QPS | 1084.60 | 1207.73 |
| cgroup memory.peak 字节 | 36261888 | 36122624 |

本样本的写入加速 1.158x，查询加速 1.114x；单轮波动明显，不能宣称相同幅度必然稳定复现。
每轮两组 Recall@10 均为1.0。整轮物理写入均为14,299,136 B（含启动/建表），写合并减少系统调用，并没有减少物理写放大。
memory.peak 包含页缓存和边界采样命令；I/O 由容器 io.stat 统计，阶段末 sync 后采集。
本机 Windows 驱动和 Docker 通信开销包含在端到端耗时中，不是赛事基线、分数或排名。

## 后续优先级与限制

生产协议现在有可执行的官方公开验证依据，已经解除此前“缺协议”的阻碍。正式29个用例仍需平台验收。
大事务的内存 WriteSet、64MiB 单事务编码上限及无界结果物化仍是已知限制，需要按实际题包负载继续处理；
不能用本次公开用例和64MiB压力测试声称覆盖所有合法输入。后续优化应先 profile、再同条件A/B，保留精确性、
恢复和内存回归；当前测量未证明存在全局最优或可安全移除持久化步骤。

原始证据见 validation/20261110/；历史20261109记录是先前开发环境与协议的记录，不能替代本版结果。
